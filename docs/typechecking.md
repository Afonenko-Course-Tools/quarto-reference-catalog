# Строгая проверка поддерживаемого кода

`tools/check-types.ts` автоматически обнаруживает собственные tracked и новые
неигнорируемые файлы через `git ls-files --cached --others --exclude-standard -z`.
Вид проверки выводится из пути и языка; ручного списка успешно проверенных файлов
нет. `vendor`, `node_modules` и gitlinks зависимостей не обходятся. Само имя собственного каталога `dependencies`
не исключает его исходники. Новые `.ts`,
`.js`, `.cjs`, `.mjs`, `.lua` и `.sh` сразу попадают в соответствующие проверки.

| Состав | Проверка |
| --- | --- |
| TypeScript, включая примеры, инструменты, тесты и программы сценариев | Deno `check` с `typecheck/deno.json` |
| `browser/navigation.js` и используемая часть браузерного API | Deno `checkJs`, DOM и `typecheck/browser.json` |
| Все `.cjs` и `.mjs`, включая собственные tools и ESLint config | TypeScript `checkJs`, Node/Playwright и `typecheck/node.json` |
| Сохранённые Lua-фильтры, словарь и тестовые программы | LuaLS с определениями Pandoc/Quarto из поставки Quarto |
| Shell-программы тестовых сценариев | ShellCheck со всеми уровнями диагностики |

`strict`, `noUncheckedIndexedAccess` и `exactOptionalPropertyTypes` применяются
ко всем TS/JS проверкам. Конфигурации также проверяют возвраты функций; Deno
проверяет переопределения методов и переходы между ветками `switch`. Конфигурации
проверок находятся отдельно от авторских проектов и не меняют запуск расширения.

`vendor` содержит сторонний код и не редактируется. `observability/bridge.ts` и
`observability/bridge.lua` принадлежат каноническому владельцу наблюдения; их
самостоятельная проверка делегирована этому владельцу. Импортируемые типы моста наблюдения
по-прежнему участвуют в проверке собственных потребителей. Наличие исключения
не является утверждением о готовности канонического моста наблюдения.

## Запуск

Для JS-проверки нужны зависимости из закреплённого `package-lock.json`:
TypeScript 6.0.3, `@types/node` 26.6.6 и Playwright 1.64.1. Для Lua нужен
`lua-language-server` 3.19.2, для сценариев оболочки — ShellCheck 0.11.0. Команды выполняются
из корня рабочего каталога:

```sh
npm ci --ignore-scripts
quarto run tools/generate-parse5-types.ts --check
quarto run tools/check-types.ts --typescript
quarto run tools/check-types.ts --browser
npm run check:node
quarto run tools/check-types.ts --lua
quarto run tools/check-types.ts --shell
```

Lua проверяется общим инструментом из gitlink `tests/dependencies/quarto-course-performance`.
Для проверок задайте `PERFORMANCE="$PWD/tests/dependencies/quarto-course-performance"`.
Явный `COURSE_PERFORMANCE_SOURCE` или `PERFORMANCE` позволяет проверить другой выбранный checkout; отдельного
списка совместимых SHA нет.
Обёртка передаёт автоматически обнаруженный собственный список `--scope`, точное исключение
канонического моста наблюдения и каталог его типов. Собственного движка LuaLS
и установщика здесь нет.
Каталоги Pandoc/Quarto определяются общим инструментом через `quarto --paths`.
`LUA_LANGUAGE_SERVER` при необходимости задаёт абсолютный путь к LuaLS 3.19.2.
Для CI применяется общий `tools/setup-lua-ci.sh` из того же рабочего каталога Performance:
он принимает новый абсолютный каталог, проверяет SHA256 и версию установки.
Контрольный `--probe` принадлежит тому же каноническому инструменту, а не локальной
копии настроек. Строгие группы `type-check`/`strong`, диагностика `no-unknown`, проверки `nil`,
объединений типов и формы таблиц сохраняются;
внешний мост наблюдения подключён как библиотека и не объявляется собственной проверкой.

Команды типов не рендерят проекты и не запускают браузер. Они не заменяют
проверки действительной установки, локальной/полной публикации, импортов, навигации и
контекста нативных обработчиков. Эти сценарии остаются отдельными проверками.

## Границы данных и дерево HTML

JSON остаётся `unknown` до существующих проверок каталога, конфигурации или
конкретного потребителя. Публичные `Catalog`, `Import`, `Exports` и `Target`
выводятся из действительных результатов проверок и проекции импорта. Второй схемы
каталога нет. Обязательные нативные метаданные HTML проверяются до создания целей;
ошибка сохраняет `QRC.OUTPUT_INVALID`, выходной путь и имя атрибута.

HTML использует реальный тип дерева parse5, включая узлы `doctype`, пространство имён и
связи родителей. Обработчик ссылок создаёт необходимые узлы штатным адаптером parse5;
поиск получает то же изменённое дерево. Дополнительного разбора HTML нет.

Deno не разрешает относительные `.js` импорты внутри исходных Node-деклараций
из `vendor` как `.d.ts`. Поэтому `tools/generate-parse5-types.ts` создаёт автономную
проекцию деклараций в `_extensions/reference-catalog/types`. Источники — только
имеющиеся сторонние parse5 7.3.0 и entities 6.0.1; версии проверяются. Генератор
сохраняет исходную структуру путей, декларации и лицензии, меняя только
относительные спецификаторы импорта `.js` на `.d.ts` и добавляя указание происхождения.
`--check` сравнивает весь результат с этими источниками. Во время исполнения по-прежнему
используется прежний сторонний parse5; npm-загрузка типов расширению не требуется.
Проекцию не редактируют вручную.

## Стиль и семантические проверки

`npm run check:formats` использует те же tracked/untracked входы и завершает
проверку ошибкой при отсутствующем CLI или его ненулевом выходе. Prettier —
единственный владелец TS/JS/JSON/YAML/CSS, StyLua — Lua, shfmt — shell.
`npm run format` применяет только форматирование. Markdown/QMD не передаются
этим форматтерам. Сгенерированные проекции и мосты наблюдения проверяются их
каноническими владельцами; `npm run check:generated` сравнивает оба генератора
QRC с сохранёнными результатами. Сторонняя проекция `types` не переформатируется.

JSON разбирается через `JSON.parse` (ровно одно значение; уникальность ключей
не доказывается). `yamllint --strict` проверяет синтаксис, дубликаты и стиль YAML;
его отступы и расстояние до комментария согласованы с Prettier. Actionlint
проверяет все workflows, включая новые, и вложенный shell через ShellCheck.
Отложенный `$sm_path` в `git submodule foreach` имеет только локальный SC2016
комментарий. Stylelint проверяет семантические ошибки CSS: неизвестные свойства,
единицы, селекторы, media features, at-rules, недопустимые цвета и повторы.

Luacheck использует Lua 5.4 и восемь публичных read-only globals Pandoc/Quarto.
Единственный writable `pandoc` ограничен `typecheck/native.d.lua`, где описывается
форма API для LuaLS. Пустая ветка пробельных узлов в `targets.equations` намеренно
сохраняет ожидание метки после выключной формулы; W542 разрешён только на её
строке. Опечатки globals, неиспользуемые значения и другие пустые ветки блокируют
проверку. Luacheck дополняет строгий LuaLS и не проверяет разрешение `require`.
ShellCheck и `bash -n` используют весь автоматически обнаруженный shell scope.
`check:node` через glob включает новые `.mjs/.cjs` в строгий checkJs; отдельный
control создаёт новый `.mjs` helper с несовместимым типом и требует TS2322.

Нужны доступные в PATH `stylua`, `luacheck`, `yamllint`, `actionlint`, `shfmt`,
`shellcheck`; Prettier и Stylelint поставляются обычными npm devDependencies.
CI устанавливает внешние CLI штатными apt/pipx/luarocks/cargo/go командами и
запускает те же npm-команды. Собственных установщиков или движков анализа нет.

Taplo — единственный владелец форматирования TOML. `check:formats` автоматически
включает новые `.toml` и выполняет `taplo format --check` и `taplo lint --no-schema`
с `.taplo.toml`; ключи не переставляются, удалённые схемы не загружаются. CLI
поставляется обычной devDependency `@taplo/cli` 0.7.0 (бинарник Taplo 0.9.0),
включая CI через существующий `npm ci`. Controls создают собственный новый каталог
`dependencies`, проверяют обнаружение TS/TOML, повтор TOML-ключа, неправильный стиль TOML и ненулевой выход
на предупреждении YAML `truthy`.

ESLint 10 и точечные npm overrides `minimatch` для ESLint/typescript-estree
устраняют известное dev-tool предупреждение без несовместимого отката parser.
Строгие правила и реальные публичные API расширения сохраняются.
